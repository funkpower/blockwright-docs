# Blockwright docs — plan

## 1. What it is

The documentation for Blockwright, in two parts:

- **Tutorials** teach someone who has never made ANSI art and has never heard of CP437. By the end they can draw, shade and light a piece, check it at 1× against the shading and craft rules, and post it to an IRC channel inside the byte budget.
- **The manual** describes everything the app does: every menu, dock, tool and option, the CLI, the file formats, the shortcuts. A reader who knows what they want looks it up here.

Tutorials link to the manual for detail; the manual links to the tutorial that teaches a feature. Neither repeats the other.

Every tutorial has the same shape:

1. **Goal**: one sentence, and the finished sample at 1× (and at 2× when it is small enough to fit the page at 2×).
2. **The idea**: the concept, with one picture.
3. **Do it**: numbered steps in Blockwright. Each step has the key or click, a picture of the canvas after it, and a window picture of the toolbox, Tool Options and any selection. A step that applies a tool or brush is a before/after pair.
4. **Check it**: what goes wrong and how it looks (a dotted diagonal, a speck, a skipped rung), from the craft rules.
5. **Try it**: a short exercise with a starting file to download (an `.ans`, or a `.bwp` when it has layers).

Pictures are the point (maintainer, 2026-11-02). Many step-by-step images, before and after every tool and brush, showing what it does and how it is used. For each brush, tutorials 04–07 show:

- its effect on a plain shape;
- each setting run on its own, as a labelled row;
- a 4–8 step worked example on a real subject;
- the common mistake.

Each tutorial ends with one piece built through all its brushes in order, every step pictured (blockwright-docs #3; layers, #2). Pictures are 2× with the 1× linked, and every one comes from a steps file, never hand-saved.

Samples are flat `.ans` only while they are one simple picture, as in tutorials 01 and 03 (maintainer, 2026-11-02). Anything more complicated is a Blockwright project (`.bwp`, Blockwright `PLAN.md` §6), with each part on its own layer the way the reader would build it, so a reader who downloads it can hide a layer and see what it adds. The page shows the composite. How layered samples are made and drawn is in §6 ("Layered samples").

Every manual page lists, per feature: where it is (menu, dock, shortcut), what each option does, its limits, and the tutorial that uses it.

## 4. What the docs need from Blockwright

Findings from reading Blockwright's `PLAN.md` and its CLI on 2026-10-23, brought up to `93be0b4` on 2026-11-05; items 5 and 6 to `de8dd90` on 2026-11-07, and item 5 to `123551f` the same day.

Checked against `30c37b9` on a three-layer project: hiding the middle layer leaves the other two. ## 5. Keeping the manual current

- A Blockwright PR that adds or changes user-visible behaviour names the manual page it affects; the docs change lands in this repo before or with the merge.
- Generated pages (shortcuts, CLI, menus) are rebuilt from the installed dev build on every docs build, so they can't go stale.
- The release checklist is the "is it done?" page of Blockwright #57, for the maintainer, not for readers: `release-checklist.md` at the repo root, built to `/release-checklist.html` from `<!-- generated: checklist -->` (§6) on every docs build. It lists every tutorial and manual page with its status in §2 or §3, the commit its `Checked:` names, and whether that is the dev CLI's commit, so it shows which pages are behind the dev build. It isn't part of the manual: no page, index, menu or pager links to it, and it carries `noindex`; the maintainer opens it by its address. The build compares commits, not their order, so a page checked against a newer commit than the CLI's shows as behind too.
- Each page states the Blockwright version it was checked against.

## 6. Build and deploy

- Pages are Markdown in `tutorials/` and `manual/`, plus the home page `index.md`, the Samples page `samples/index.md` (`TOP_PAGES` in `scripts/build`) and an `index.md` per section. `scripts/build` turns them into `site/`: one Python 3 script on [Python-Markdown](https://python-markdown.github.io/) (the distribution's package: `python-markdown` on Arch, `python3-markdown` on Debian and Ubuntu, `python3-markdown` on Fedora), with the `meta`, `extra`, `toc` and `sane_lists` extensions. No site generator, no JavaScript, no network. `site/` is build output and isn't tracked.
- **Why this:** pages stay plain Markdown that reads on the forge as it is; the only dependency is a packaged library; the output is static HTML that works from a web root, a subdirectory or a file browser, which is also what the in-app help (Blockwright #210) needs: `--help-bundle` makes it from the same build (below).
- **Publishing a page:** a page carries a meta block. `Title:` names it in the lists (else its first heading). `Checked: Blockwright 0.1.0 (30c37b9)` says which build it was checked against and publishes it; a page without `Checked:` is a stub, listed as "not written yet", and a link to a stub fails the build.
- **Maintainer's pages:** a page named in `STANDALONE` at the top of `scripts/build` (only `release-checklist.md`) sits at the repo root and is built at the site root, always, with no `Checked:`. It belongs to neither section, so no index, list, menu or pager names it; it carries the site menu with nothing marked, and a `<meta name="robots" content="noindex">`.
- **Pictures of pieces:** `![alt](../samples/<tutorial>/<file>.ans "2x")` renders the `.ans` with `blockwright-cli render --scale 2` (the title is the scale, `1x` to `8x`; none means 1×), puts the PNG in its place, links it to the `.ans`, and copies the `.ans` into the site. A `.bwp` is drawn the same way, as its composite, and links to the `.bwp`. The PNG keeps the sample's whole name (`final.ans-2x.png`, `final.bwp-2x.png`), so a flat `.ans` and a project of the same name can sit in one folder, as the flat export beside its project will; failing the build on the clash instead would forbid that pairing. Any other image is a `.png`, copied as it is; an image of any other kind fails the build, an unpacked project directory included, since a picture links to one file the reader downloads. Pictures are never edited by hand.
- **Other files:** any other relative link (a `.bwp` or an `.ans` no page draws, a Try-it file) names a file in the repo, which the build copies into the site at the same path.
- **Generated parts:** `<!-- generated: cli-help -->` is replaced by `blockwright-cli --help`; `<!-- generated: shortcuts -->` by a table per menu (an `<h3 id="keys-<menu>">` each, in the order `--list-actions` first names the menu) of every action the app lists: its text, its shortcuts and hint keys as `<kbd>` (`Ctrl`+`Z`), `(standard)` after keys from Qt's standard keys, and what it does (the status tip, else the tooltip without its leading name and keys, then where it's offered), after a line naming the app's version and Qt. A marker goes at the start of a line of its own, in column 0: not indented, not in a list item or blockquote. It is written exactly as shown: lowercase, single spaces. The build replaces markers inside Python-Markdown, after it has set fenced code aside, so a marker is left as written exactly where Markdown shows it as code (a closed fence, an indented block), and a page can show one. The brush tutorials, 04–07, show what a brush does to the canvas, so their step images come from `blockwright-cli replay` steps files and are never imitated with `scripts/ansi.py`.
- **No Publish or Send** (maintainer, 2026-11-14, with Blockwright #494): File > Publish to Library and File > Send to WeeChat fitted one person's setup, not a general editor, so the app drops them and the pages describe a piece reaching IRC through Export IRC Text and `export --irc`, saved as a project or an `.ans`. The `efnet-weechat` preset, the IRC View's cuts, measuring a line as WeeChat's ascii script sends it, Export Micron and the Library dock stay.
